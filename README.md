# flight-sniper

Личный монитор цен FRU/ALA → HKT/DPS на октябрь 2026. Интерфейс — только Telegram.
Стоимость эксплуатации — $0/мес.

## Как это работает

| Воркфлоу | Расписание | Что делает |
|---|---|---|
| `scan` | раз в час, 4 прохода внутри рана | запросы к кэшу Aviasales (8 в режиме one_way, 16 для round-trip), запись истории; в каждом проходе следом же обрабатываются команды из Telegram |
| `digest` | 03:00 UTC (09:00 Бишкек) | сводка по 4 маршрутам в Telegram |
| `commands` | вручную (`workflow_dispatch`) | тот же обработчик команд, что и внутри `scan`, — для отладки без ожидания цикла |
| `keepalive` | раз в 20 дней | пустой коммит: GitHub отключает cron после 60 дней без активности |
| `tests` | на push и PR | pytest + проверка синхронизации БД |

База живёт в orphan-ветке `data`: каждый ран перезаписывает её одним коммитом без
родителя. `main` содержит только код и не растёт от бинарника.

### Почему `scan` не запускается по частому cron

Расписание `scan` было `"5 */4 * * *"`, затем — в погоне за более частыми
находками — `"*/30 * * * *"`. Оба варианта не сработали на практике: планировщик
GitHub Actions не гарантирует частые интервалы. Замер на живом репозитории —
при четырёхчасовом расписании запуск, ожидавшийся в 03:05, фактически произошёл
в 03:42 (сдвиг 37 минут); после перехода на получасовое расписание за 40 минут
не запустилось ни разу — слот 07:00 был пропущен целиком. Задержка планировщика
оказалась сопоставима с самим интервалом, а часть запусков просто терялась.

Решение — не бороться с планировщиком, а перестать от него зависеть: `scan`
запускается раз в час (`cron: "0 * * * *"`, частые старты одного воркфлоу
устойчивее к сдвигу — пропустил планировщик один раз, потеряли час, а не
полдня) и внутри одного рана делает 4 прохода с паузой 14 минут между ними,
занимая ран ~56 минут — так следующий часовой старт не накладывается на
предыдущий.

Заодно в каждом проходе после скана сразу обрабатываются команды из Telegram —
`commands` выполняется в теле того же цикла, а не отдельным воркфлоу. Раньше
`scan` и `commands` были двумя воркфлоу, синхронизированными общей
`concurrency`-группой на orphan-ветке `data`, — при длинном ране (а он теперь
длинный) обработка команд встала бы в очередь на час. Слияние в одну итерацию
убирает и очередь, и саму возможность гонки за базу.

## Секреты

Settings → Secrets and variables → Actions:

| Секрет | Где взять |
|---|---|
| `TP_TOKEN` | travelpayouts.com → Инструменты → API |
| `TG_BOT_TOKEN` | @BotFather |
| `TG_CHAT_ID` | @userinfobot |

Токен Travelpayouts передаётся заголовком `X-Access-Token`, а не query-параметром:
иначе он попадал бы в текст сетевых исключений, а оттуда — в базу, которая
публикуется в ветке `data`.

## Локальный запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt

export TP_TOKEN=... TG_BOT_TOKEN=... TG_CHAT_ID=...
.venv/bin/python monitor.py backfill   # один раз, на пустой базе
.venv/bin/python monitor.py scan
.venv/bin/python monitor.py digest
```

Тесты: `.venv/bin/pytest` и `bash tests/test_db_sync.sh`. Сеть не нужна — все
внешние вызовы замоканы.

## Метрика

Всё сравнение — в `landed_usd`:

```
landed_usd = price_local × fx_rate × (1 + fx_markup[currency])
```

`fx_rate` (USD за единицу валюты) пишется в каждую строку и обновляется при
каждой повторной встрече оффера, поэтому падение цены всегда отличимо от
движения курса.

Три уровня сравнения:
- аномалия во времени — внутри одного рынка, в локальной валюте;
- арбитраж между рынками и вердикт BUY — по `landed_usd`.

## Устройство

| Модуль | Ответственность |
|---|---|
| `monitor.py` | CLI-вход: `scan`, `backfill`, `digest` |
| `src/config.py` | дефолты из `config.yaml` + оверрайды из таблицы `meta` |
| `src/models.py` | `PriceRecord` — единственный тип обмена между слоями |
| `src/store.py` | SQLite: схема, вставка с дедупом офферов, выборки, `meta` |
| `src/fx.py` | курсы валют, `landed_usd` |
| `src/sources/aviasales.py` | Data API v3: парсинг, фильтры, HTTP, скан, бэкфилл |
| `src/rules.py` | перцентили, baseline, светофор |
| `src/digest.py` | сборка и рендер текста дайджеста |
| `src/notify.py` | транспорт до Telegram |
| `src/runner.py` | оркестрация одного рана |

Изменяемое состояние (`abs_threshold_usd`, пауза, время последнего скана) живёт в
таблице `meta`, а не в `config.yaml`: три воркфлоу, коммитящие один файл в `main`,
гонялись бы за него.

## Ограничения

Кэш Aviasales — сигнал, а не оферта: цены отражают чужие поиски за последние ~48
часов и на выкупе могут отличаться. Запись остаётся «свежей» весь TTL, поэтому
подорожавший вариант ещё какое-то время виден по старой цене — дайджест не
утверждает, что тариф доступен прямо сейчас.

## Команды бота

| Команда | Что делает |
|---|---|
| `/now` | сводка прямо сейчас |
| `/status` | состояние сканера, объём истории, порог, маршруты |
| `/threshold 220` | показать или изменить порог BUY |
| `/pause`, `/resume` | остановить и вернуть оповещения |
| `/route add TAS HKT` | добавить маршрут |
| `/bought`, `/mismatch` | отзыв по последнему оповещению |
| `/help` | справка |

Ответ приходит на следующем проходе цикла `scan` — до 14 минут. Сервера у
проекта нет, команды забираются через `getUpdates`.

## Почему не Amadeus

Изначально планировалось подтверждать цены через Amadeus Self-Service. Живые данные
это отменили: лучшие цены везёт AirAsia X — лоукостер, которого в GDS нет, а продают
их посредники (City.Travel, Trip.com), чьи тарифы там тоже отсутствуют. Amadeus
отвечал бы «не подтвердилось» именно на лучших находках. Подтверждение делается
точечным повторным запросом к тому же бесплатному кэшу по конкретной дате.

Проверка гипотезы «у лоукостера напрямую дешевле» тоже не подтвердилась: на
airasia.com тот же маршрут стоил $275 против $171 у посредника, а сам сайт давно
превратился в такое же агентство (AirAsia MOVE), торгующее чужими рейсами.
